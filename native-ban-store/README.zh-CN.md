# Ban Store：Ban IP 专用存储组件

版本 0.1.0，C++17，直接集成到 Ban Agent，交付 `libscdn-ban-store.a`。它只存封禁 IP 及其必要的期限、解封水位、去重回执、集群恢复和审计投影游标；其他插件不使用它保存站点配置、缓存正文或业务数据。

它采用内存索引与可选追加日志，不依赖 SQLite、Redis 或另一存储进程。没有 SQL、Redis 协议、任意用户数据库、脚本、发布订阅、复制服务或新增 TCP 端口；跨机全量同步继续由现有 Ban/Sync 协议负责。

## 两种模式

| 模式 | 活动状态 | 确认与重启 |
| --- | --- | --- |
| persistent（默认） | 内存索引，追加事务日志及原子快照 | 事务 `fdatasync` 完成后才确认；从快照和完整事务恢复 |
| memory | 只在 Agent 内存中，不打开状态 AOF 或快照 | 确认仅表示本进程已接受；重启丢失本机状态，Node 从在线 Master 重新获取完整集合 |

Agent 的权威 Master 要求 persistent，防止遗忘全局解封和单调序号；Node 可选择两种模式。memory Node 重启时使 HTTP 视图重新进入等待状态，保留已有 pinned 内核期限直到接收当前完整表，再应用新集合。现有 Nginx Worker 通过明确的 volatile-reset 握手重新编号未确认事件，保留原观察时间和旧代际，避免序号空洞或复活旧证据。

两份指定审计日志仍按 Ban 要求输出，memory 不把这些日志当作状态恢复来源；重启开始独立日志 session。内存模式不是“磁盘掉电后仍保证回执”的承诺。线协议旧名 `durable` 字段是非零回执 ID；实际落盘保证必须结合 status.storage.mode/durable 判断。

## 配置

在现有 Agent `policy.json` 根对象加入：

```json
"storage": {
  "mode": "persistent",
  "max_entries": 1048576,
  "max_memory_mb": 512,
  "checkpoint_mb": 64
}
```

Node 改成 `"mode": "memory"` 即使用纯内存状态。省略整个 storage 时采用上述默认值；max_entries 范围 65,536–16,000,000，max_memory_mb 为 16–4096，checkpoint_mb 为 1–1024。模式和路径变更须维护迁移；容量/checkpoint 参数只在启动时生效，热加载会明确拒绝，重启可继续使用符合新配额的已有状态。默认状态目录仍使用现有 state_dir。

max_entries 包含 IP、回执等全部内部条目，max_memory_mb 分别限制带固定条目开销的活动索引和全部待提交集合（各一份预算），**不是操作系统 RSS 的硬限制**。事务编码、哈希表桶和快照准备还占用有界临时空间。每值最多 16MiB、每事务编码最多 64MiB，不能用一个无限大的事务绕过配额。memory 提交不生成 AOF 编码或内容摘要。

存储容量与执行容量独立：存储核心验证百万条 IP；当前 Ban Agent/eBPF/共享视图仍有其 4,096 条活动记录上限。该存储基准不表示整个集群已经能够执行百万条封禁。

## 索引、事务与持久化

- IP、生产者和回执点查使用哈希索引；审计、outbox 和按 IP 分组的证据使用有序索引。普通查询不访问状态磁盘。
- 事务只保存变更集合，支持回滚与内部 savepoint，不复制整个 IP 表。容量和需要的节点分配在持久提交前检查/准备。
- Agent 合并一轮 poll 中至多 128 个来源事件，先一次持久提交整个批次，再核对内核、投影日志并发送回执。没有为了合批额外等待固定时间；孤立事件仍可独立提交。
- `ban-store.aof` 包含版本化快照和追加事务。独立头部校验、SHA-256 内容校验及前序摘要链检查边界和顺序，损坏的长度字段不会被当作正常半写尾部；它们用于损坏检测，不是针对同 UID 管理员修改的认证机制。
- 重启只移除最终未写完整的事务尾部；完整帧校验错误、序号断裂或快照损坏直接拒绝，不把已确认数据静默当作可丢弃尾部。
- checkpoint 在私有临时文件中顺序写入，文件同步后原子 rename，再同步目录。替换后的目录同步失败会停止后续写入，避免继续写向旧 inode。
- 追加部分超过 checkpoint_mb 后进行压缩，门限不把快照本身算成新增日志，避免大表每次写入都重建快照。压缩为同步维护工作，大表下有暂停成本；失败保留旧日志，达到有界日志上限后拒绝继续增长。

日志投影成功后回收已投影的内部审计条目，保留各文件尾记录供恢复核对；审计高水位独立保存，回收不会把回执或执行水位退回零。完整历史留在指定事件/IP 日志中。单份日志已写入而另一份或游标事务失败时，重试从核验过的文件尾部继续，不重复追加。

可通过现有受限管理 Socket 执行 `banctl.py --socket /run/scdn-ban/admin.sock checkpoint` 主动生成快照；备份仍须停止写者后取得一致文件。snapshot 操作仅供 authority 导出当前签名全量表，不提供任意键修改接口。

## 权限、恢复与升级

持久目录必须是 Agent 所有的 0700，AOF 和单写者锁要求 0600、普通文件、单硬链接，父目录与文件均拒绝符号链接。Agent 的原 state/runtime 独占锁继续生效。I/O 错误会使 writer 停止接收新写入，必须恢复存储并重新打开；不会对失败提交发送成功回执。

旧 SQLite 文件不会被读取、覆盖或删除。检测到 state.sqlite 或其伴随文件会拒绝启动并提示离线迁移；本版不包含 SQLite 兼容引擎或自动转换器。已有权威状态需先保留一致备份并完成可信的离线迁移；新 Node 可用新私有目录从当前 Master 重建。不能清空仍在使用的权威水位以绕过检查。

升级必须同步更新 Agent 与 Nginx Ban 模块；memory-reset 握手需要新 Worker 代码。持久模式同 boot 重启保留已有回执、固定期限和 pinned 视图；memory 的丢失语义是明确选择。文件系统必须提供实际的同步和原子替换语义，未验证任意网络文件系统或硬件掉电行为。

## 构建与验证

```sh
sh native-ban-store/tools/build-store.sh /tmp/scdn-ban-store
python native-ban-store/tests/run.py --build /tmp/scdn-ban-store --count 100000 \
  --report /tmp/ban-store-results.json
sh native-ban/tools/build-agent.sh /tmp/scdn-ban
```

独立组件只需 C++17 和 OpenSSL libcrypto。Agent 的其余 libbpf/json-c/libcurl 依赖保持；构建与实际链接不使用 SQLite。Store 由所属 Agent 串行调用，多线程客户必须遵循同一所有权锁，不能把它当成无锁并发容器。

覆盖事务、savepoint、配额、日志半写、完整损坏、同步/rename/目录同步故障、单写者、权限、快照压缩、百万条 IP 和重启值校验。真实内核测试继续覆盖集群、固定到期、解封和恢复，另验证内存 Node 重启后现有 Worker 继续上报。基准只衡量存储组件，测试环境与结果在本次验证记录中列明。

## 本地百万 IP 基准

以下为 WSL2 Linux x86_64、20 vCPU、Linux /tmp 文件系统的一次最终实现实测；每批 1,024 条，写入 1,000,000 条合成 IPv6 IP，随机查询 100,000 次，再删除一半并验证重启后剩余 500,000 条。测试不使用 SQLite 或 Redis，不代表生产容量或尾延迟。

| 项目 | memory | persistent |
| --- | ---: | ---: |
| 写入 100 万条 | 1.851 秒 | 10.422 秒 |
| 随机查询 10 万次 | 133.3 毫秒 | 126.6 毫秒 |
| 删除 50 万条 | 1.177 秒 | 6.921 秒 |
| 手动快照（剩余 50 万条） | 无落盘 | 549.5 毫秒 |
| 重启恢复（剩余 50 万条） | 不保留状态 | 1.914 秒 |
| 整个工作负载的数据同步 | 0 | 1,958 次，含 checkpoint |
| 进程峰值 RSS | 约 270.1 MiB | 约 270.2 MiB |

原始指标、断言数量、三种构建和已知边界见[验证记录](../docs/validation-ban-store-20261116.json)。
